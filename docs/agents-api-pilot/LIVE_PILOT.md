# Opt-in live connection and single-turn smoke

This candidate adds actual application-side SDK streaming and rootless Podman
callbacks. Importing it does nothing. **Calling `run_live` contacts OpenAI and
starts a container. It has not been run against an API or VPS.** The unit tests
use fake API/Podman implementations, synthetic keys and local temporary files.
They do not establish container, nested-sandbox, credential or billing acceptance.

The first workload is deliberately small: create/read a sentinel with Python in
an empty disposable workspace. This is not the existing clamp bug-fix task.
The workspace is tmpfs, so image content at `/workspace` is hidden; there is no
repository checkout, seeding, patch extraction or independent test verification.
A completed cloud turn is reported separately from local cleanup, and
`result_verified` remains false. Even a model claim of `SYNTHETIC_OK` is not an
independent file or test observation.

## Required approval and prepared inputs

Do not run until the operator has approval for the specific synthetic task,
model, positive USD-cent `spend_control.limit`, one API session/turn, distinct
restricted environment-key use, and this exact disposable runtime/image profile.
Account/model/API access and applicable credit balance remain separate account
checks. The limit is requested and read back; this code does not establish an
absolute billing ceiling or zero cost after cancellation.

The target is an **already prepared** local rootless Podman 4.9.3 installation,
running as the verified nonroot worker in its own dedicated application process.
`PreparedTarget.image_id` is the exact local image content ID, not a mutable tag
or an OCI index digest. `acceptance_id` references operator-retained evidence for
that exact image, runtime and launch profile. It is an explicit input, not proof
generated by this module. The launcher checks effective UID, rootless/version
readbacks and private runtime directories before cloud creation; it disables
Podman remote mode and never pulls an image or provisions dependencies.
All Podman calls for a **new** attempt explicitly use
`--remote=false --cgroup-manager=systemd`. This is per-process selection, not an
edit to `containers.conf` or a change to existing containers. The existing info
check now requires exactly `true systemd v2` from the Go template
`{{.Host.Security.Rootless}} {{.Host.CgroupManager}} {{.Host.CgroupsVersion}}`.
The plural `CgroupsVersion` is the Podman 4.9.3 Go field, despite the singular
JSON key. A fallback manager, v1, failed read or unknown response blocks creation.
Created-container inspection and live cgroup capture also require effective
`HostConfig.CgroupManager=systemd`; a CLI flag alone is not proof.

Use an already available worker user manager/bus and delegated controllers.
Podman can discover an existing bus from the selected `XDG_RUNTIME_DIR` without
adding a D-Bus address to the caller's clean environment. Successful `info` does
not prove that the bus works or delegation is sufficient; scope creation and the
unchanged live resource/cgroup checks must still pass. Missing facilities stop
the attempt. The launcher never enables linger, starts or reconfigures host
user-manager services, changes delegation/permissions, or retries with cgroupfs
or rootful execution. Any required host change needs separate explicit approval;
security-sensitive changes require action-time approval.

Prior cgroupfs attempts must be reconciled separately with their original
manager/context before a fresh attempt. Do not point this systemd-only wrapper
at them or reuse their acceptance evidence. Retain a fresh acceptance record for
the exact systemd profile. Podman warns that operations on containers created by
another cgroup manager can fail.
The selected runtime home/directory, their ancestors and Podman configuration
must remain under trusted exclusive control throughout the attempt. The code
rejects symlink paths and checks final-directory ownership/mode, but does not
protect against replacement through writable or foreign-controlled ancestors.

The image must contain a trusted compatible Codex at `/opt/agents/bin/codex`,
Python 3 on the fixed PATH, and everything needed for **nested** Codex sandboxing.
A full official Codex package preserves its manifest and helpers; an existing
trusted compatible `bwrap` on PATH is also a documented option. The earlier
bare-binary no-key outer-container smoke is insufficient. Its `0.0.0` package
metadata is not a release-version match. Do not fabricate a manifest, skip a
sandbox failure, grant capabilities, use `--privileged`/unconfined policies,
change sysctls, or modify production services to make this candidate pass.

The exact fixed profile must be accepted with a no-key nested-sandbox test first:
read-only image, UID/GID 65534, dropped capabilities, no-new-privileges, ordinary
existing seccomp/AppArmor policy, private PID/IPC/UTS/cgroup namespaces, tmpfs
workspace/home/tmp, and the verified user-namespace support needed by Codex.
`auto_review` is a server review setting, not by itself sandbox configuration.
A new image/setup/security change requires its own approval if not already covered.

## Network and key boundary

The live profile uses local rootless `slirp4netns:allow_host_loopback=false` and
existing DNS. **It is not an endpoint allowlist.** It permits broader outbound
traffic; denying the host-loopback shortcut does not isolate all host/private
network addresses. Approval must cover that standard disposable-network scope,
or an independently prepared and verified narrower network policy must replace
this candidate before use. No firewall, global network or production policy is
changed here. Documented control destinations include `api.openai.com:443` and
`codex-cloud-environments.chatgpt.com:443`; listing them does not enforce them.
The agent instruction against network use is defense in depth only.

The caller supplies keys explicitly from an approved secure source. Never put
keys in command-line arguments, source, reports, shell history or environment
variables. The application key stays in the application process and is not
passed to Podman. A distinct environment-only key goes once through the attached
container stdin to official `--registration-bearer-stdin`, never container argv,
environment or a mounted file. Its authorization scope must be checked separately;
string inequality cannot prove scope. The returned registration URL is passed
unchanged after the existing HTTPS `api.openai.com` check; do not log it or dump
raw Podman inspect records. The worker receives no host directory mounts, runtime
socket, production configuration or authentication home.

Container stdout/stderr and Podman stderr are discarded, and the logging driver
is `none`. There are no raw provider-event or key logs. Caller-side failure
handling must also avoid printing exceptions, configuration, SDK objects or
tracebacks containing sensitive state.

## Exact entry and lifecycle

A trusted caller constructs a `Task` with the existing repository/base metadata,
`instructions=SYNTHETIC_INSTRUCTIONS`, `allowed_paths=('pilot_sentinel.txt',)`,
`output_bytes=65536`, and `timeout_seconds` at most 180. Repository/base values
are admission metadata only; no repository is connected or mounted. Choose the
model and positive spend limit explicitly with `Plan(task, model,
spend_limit_cents=approved_cents)`. Use a new 64-lowercase-hex attempt ID and an
existing private 0700 journal directory owned by the application user.

The callable entry is:

```python
import asyncio

from ops.bounded_worker.agents_live_pilot import (
    PreparedTarget, SYNTHETIC_INSTRUCTIONS, run_live,
)

# All values are prepared/approved in this dedicated caller beforehand.
# Keys are arguments in memory from the authorized source, not argv or env lookup.
result = asyncio.run(run_live(
    plan, attempt_id, journal_directory,
    PreparedTarget(image_id, runtime_home, runtime_dir, acceptance_id),
    application_key=application_key, environment_key=environment_key,
))
```

There is no auto-executing command-line mode and no default key lookup. Required
application dependencies are the source-verified official `openai==3.47.0`
package and its dependencies plus the supported legacy `httpx` package. This
module installs nothing. `OPENAI_CUSTOM_HEADERS` presence blocks startup because
the SDK otherwise merges it. Explicit SDK options avoid ambient key/scope/base
URL defaults, proxies, retries and redirects.

The sequence is:

1. Verify the selected rootless local runtime and dependency inputs.
2. Durably reserve creation, then create one self-hosted session with no input.
3. Open its authenticated official SDK event stream, with a 64 KiB raw response
   cap **below** SSE parsing, no compression, no replay/reconnect, and no retries.
4. Durably reserve executor launch. Create a deterministic bound container with
   `--pull=never`, inspect identity/policy, attach its registration stdin, and
   capture its exact running host cgroup and configured memory/CPU/PID limits.
5. Wait for the exact environment-connected event. Refresh session/environment
   policy, durably reserve input, then submit exactly one sentinel task.
6. Observe the exact root-turn terminal event or block on disconnect, malformed
   data, quiet stream, timeout or uncertain outcome. HTTP 202 is acceptance only.
7. On an uncertain/nonterminal submitted turn, attempt cloud cancel once. Local
   stop and independent empty readback happen separately even if cancel fails.

The stream quiet timeout defaults to 10 seconds, with a 180-second maximum work
window. Blocking serial controller calls have main-thread Linux signal deadlines,
not abandoned background threads that can later submit input. This entry requires
an otherwise idle dedicated process with no active real-time signal timer. Cleanup
has separate bounded budgets, so total elapsed time can exceed the work window.
Podman's own 180-second timeout is defense in depth, not proof of cleanup or cloud
termination. Kernel-uninterruptible I/O or process crash cannot be repaired by a
Python watchdog. A timeout never authorizes retrying an uncertain write.

Each tmpfs has 64 MiB capacity, mode 0700, private ownership and explicit
nosuid/nodev/noexec. Container limits are 1 GiB memory+swap cap, one CPU, 64 PIDs
and a five-second stop grace. Inspection validates identity/labels and selected
policy fields; it supplements the retained exact-profile acceptance, not a
complete independent OCI/security audit. Runtime-added environment fields are
not blanket-allowed; mappings must match exactly, without duplicate names.

Capture accepts the host PID's canonical unified cgroup membership at the bound
scope or a component-bounded descendant: Podman 4.9.3 normalizes inspect paths
to the enclosing full-ID scope. For the verified crun 1.14.1 profile, controls are
read from the exact observed PID-membership directory, opened component by
component beneath the bound scope with no symlinks or child search. Require
1 GiB memory, zero additional swap, 64 PIDs, CPU quota/period 100000/100000,
and zero burst when that optional kernel interface exists. The enclosing scope
FD remains the recursive cleanup boundary, not just the payload's FD. Exact
private PID/cgroup namespace and non-systemd container mode are checked along
with the existing nonroot/no-capability/no-host-mount profile. Its retained OCI
acceptance must establish read-only cgroup access with no writable alternative.
The no-key READY/GO harness now checks its trusted PID1's actual mountinfo before
GO in that same attempt; a prior mount audit is not a prerequisite for starting
that fixed bootstrap. The live path still requires the retained successful
result for its exact image/runtime/profile. Inspect policy alone is not a mount
audit. Sibling/prefix/traversal
and namespace-root mismatches remain rejected. `resource_diagnostics` records
bounded numeric scope/payload controls and fixed error states before a failure;
it does not reconstruct missing historical values. See `NESTED_ACCEPTANCE.md`
for the pinned source contract, optional-burst semantics and limitations.

Cleanup requires exact stopped-container identity plus the saved cgroup's
`populated 0`, or removal of that previously held kernel cgroup inode. Losing
startup evidence leaves cleanup unverified. Stopped container metadata is retained
for reconciliation; this wrapper does not remove containers/images. No worker
output is copied off the tmpfs. Separate approved operator cleanup can remove the
verified stopped target; do not remove an unrelated target or purge evidence.

The journal prevents replay, but does not persist session/container recovery
records. Restart recovery is **not implemented**. Keep the journal and reconcile
uncertain cloud and local state manually; creating a fresh attempt is not recovery.
SDK stream close, local stop and cloud cancel are distinct operations.
The returned report retains known attempt/session/environment/turn/container IDs
for private operator reconciliation, including when opening the stream fails
after session creation, plus safe numeric resource diagnostics. It excludes
remote URLs, keys and raw events. Retain this
report privately; a crash before return can still lose those in-memory identities.
